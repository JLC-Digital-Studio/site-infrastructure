# JLC Digital Studio Site Infrastructure

Reusable GitHub Actions workflows for JLC Digital Studio static websites.

The main reusable workflow is:

```text
.github/workflows/deploy-static-site.yml
```

It is called by the individual site repositories rather than duplicated into each site.

## What the reusable workflow does

The standard deployment flow is:

```text
Check out site repository
→ Set up Node
→ npm ci
→ npm run check
→ npm run build
→ add deployment metadata
→ validate deployment target
→ configure SSH
→ rsync build output to the server
```

### Caller requirements

A site repository using this workflow must provide:

- `package.json`
- `package-lock.json`
- `npm run check`
- `npm run build`
- a build output directory, normally `dist/`

The calling repository also supplies its own deployment host, Hestia user,
deployment path, SSH host key, and private deployment key through GitHub
Actions variables and secrets.

## Deployment metadata

After the site build completes, the reusable workflow generates:

```text
last-commit.html
```

inside the build directory before deployment.

The page contains:

- the short Git commit SHA used for the deployment; and
- the commit date in human-readable U.S. Eastern Time, using EDT or EST
  automatically as appropriate.

It also includes `noindex, nofollow` so search engines are discouraged from
indexing the operational metadata page.

For a deployed site, check:

```text
https://<domain>/last-commit.html
```

Because the page is generated by the deployment workflow, do **not** add
`last-commit.html` manually to individual site repositories.

# Maintaining the shared deployment workflow

## Why site repositories use a pinned commit SHA

Site repositories call this workflow using an exact Git commit SHA:

```yaml
uses: JLC-Digital-Studio/site-infrastructure/.github/workflows/deploy-static-site.yml@<COMMIT-SHA>
```

For example:

```yaml
uses: JLC-Digital-Studio/site-infrastructure/.github/workflows/deploy-static-site.yml@11e9837bd8f1601ee579e4a4086d9291fadc95e5
```

The value after `@` is the exact version of the shared workflow that the site
will use.

This is intentionally **not**:

```yaml
@main
```

Using a pinned SHA means an infrastructure change cannot unexpectedly change
every site's deployment behavior at once.

### What "repinning" means

Repinning means replacing the old SHA after `@` with the SHA of the newly
approved `site-infrastructure` commit.

For example:

```text
OLD
deploy-static-site.yml@aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa

NEW
deploy-static-site.yml@bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
```

Changing `site-infrastructure` alone does **not** update existing sites.
Each caller continues using its current pinned version until its workflow file
is repinned.

# Procedure: change site-infrastructure

Use this procedure whenever editing
`.github/workflows/deploy-static-site.yml`.

## 1. Edit site-infrastructure

Open the local `site-infrastructure` repository in VS Code and make the
workflow change.

Review the diff:

```powershell
git status
git diff
```

Commit and push to `main`:

```powershell
git add .
git status
git commit -m "Describe infrastructure change"
git push
```

> **Why main?** `site-infrastructure` is the versioned source of the reusable
> workflow. Individual sites are protected from immediate adoption because
> they reference exact commit SHAs rather than `@main`.

## 2. Get the new infrastructure commit SHA

After the push succeeds, get the full 40-character SHA:

```powershell
git rev-parse HEAD
```

Example:

```text
11e9837bd8f1601ee579e4a4086d9291fadc95e5
```

You can also copy the full commit SHA from GitHub.

> Use the **full commit SHA**, not the shortened seven-character form used for
> display purposes.

## 3. Update template-site

Update both deployment workflow files in `JLC-Digital-Studio/template-site`:

```text
.github/workflows/deploy-staging.yml
.github/workflows/deploy-production.yml
```

Find:

```yaml
uses: JLC-Digital-Studio/site-infrastructure/.github/workflows/deploy-static-site.yml@<OLD-SHA>
```

Replace only `<OLD-SHA>` with the new full SHA.

Because `template-site` has both `main` and `staging`, keep the workflow
pin current on **both branches**.

### Why update template-site first?

New repositories created from the template inherit the workflow files stored
there. If the template is not repinned, newly created sites can start with an
older infrastructure version.

# Procedure: repin existing sites

For each existing static site using the shared workflow, update the workflow
pin on the site's **staging branch**.

Do not routinely edit the live site's `main` branch directly.

The standard progression is:

```text
new site-infrastructure commit
        ↓
repin site's staging branch
        ↓
staging deployment
        ↓
verify staging
        ↓
staging → main pull request
        ↓
production uses the tested infrastructure version
```

This preserves the same staging-first safety model used for site-content
changes.

## 4. Find every repository that calls site-infrastructure

Do not rely on memory.

### GitHub CLI method

From a PowerShell terminal authenticated with GitHub CLI:

```powershell
gh search code "site-infrastructure/.github/workflows/deploy-static-site.yml@" --owner JLC-Digital-Studio
```

Review the results and identify the static-site repositories using the shared
workflow.

### GitHub website method

Search the `JLC-Digital-Studio` organization for:

```text
site-infrastructure/.github/workflows/deploy-static-site.yml@
```

Check each matching deployment workflow.

> A repository that does not contain a caller for
> `deploy-static-site.yml` does not need to be repinned for this workflow.

## 5. Repin a site's staging branch

Open the site repository locally and make sure you are on `staging`:

```powershell
git switch staging
git pull --rebase
```

Edit:

```text
.github/workflows/deploy-staging.yml
.github/workflows/deploy-production.yml
```

Replace the old infrastructure SHA with the new SHA in both files.

Then review:

```powershell
git diff
git status
```

Commit and push:

```powershell
git add .github/workflows/deploy-staging.yml .github/workflows/deploy-production.yml
git status
git commit -m "Update shared deployment workflow"
git push
```

> **Why update both workflow files on staging?** The staging branch should
> already contain the production workflow change that will later be promoted
> to `main`. This ensures the eventual production deployment uses the same
> infrastructure version that was tested during staging.

## 6. Verify the staging deployment

A push to `staging` should start the staging deployment automatically.

In GitHub:

1. Open the site repository.
2. Open **Actions**.
3. Open the latest **Deploy staging** run.
4. Confirm all relevant steps succeed.

Typical steps include:

```text
Install dependencies
Run checks
Build site
Add deployment metadata
Validate deployment target
Configure SSH
Deploy site
```

Then inspect the staging site.

Also check:

```text
https://<staging-domain>/last-commit.html
```

Confirm that the displayed commit matches the site commit that triggered the
deployment.

### If staging fails

Do not update production just to see whether it works there.

Open the failed Actions run and identify the failing step.

Correct the problem on `staging`, commit, push, and retest until staging
deploys successfully.

## 7. Promote the tested infrastructure version to production

Once staging is healthy, use the normal site promotion process:

1. Open a pull request from `staging` to `main`.
2. Review the workflow changes.
3. Merge the PR.
4. Confirm the production deployment succeeds.
5. Check the production site's `last-commit.html`.

Do **not** separately hand-edit the production workflow SHA after the merge.
The tested workflow files should arrive through the normal
`staging → main` promotion.

# Which repositories need to be changed?

There are two categories.

## template-site

Update:

- `main`
- `staging`

This keeps future repositories current.

## Existing deployed static sites

Update:

- `staging` only during the repin operation

Then allow the normal pull request to carry the change to `main`.

Do not assume every repository in the organization uses this workflow. Search
for callers first.

---

# When a site should NOT be repinned yet

It is acceptable to leave a site on an older infrastructure SHA temporarily.

Examples:

- the new infrastructure change has not been tested yet;
- the site is in the middle of unrelated production work;
- the site has custom deployment requirements; or
- a problem was discovered during staging.

The pinned SHA is a feature: it allows sites to adopt shared infrastructure
changes deliberately rather than simultaneously.

---

# Quick maintenance checklist

After changing `deploy-static-site.yml`:

- [ ] Change committed and pushed to `site-infrastructure/main`
- [ ] Full new infrastructure commit SHA copied
- [ ] `template-site/main` repinned
- [ ] `template-site/staging` repinned
- [ ] GitHub organization searched for existing callers
- [ ] Each applicable site's `staging` workflows repinned
- [ ] Staging Actions runs succeed
- [ ] Staging sites verified
- [ ] `last-commit.html` checked where useful
- [ ] Each site promoted through its normal `staging → main` pull request
- [ ] Production Actions runs succeed
- [ ] Production sites verified

## Operational principle

`site-infrastructure` defines shared deployment behavior, but each site
chooses exactly which version of that behavior it uses through its pinned
commit SHA.

That gives JLC Digital Studio centralized deployment logic **without**
sacrificing per-site change control.
